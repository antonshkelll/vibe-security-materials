# ТЗ: мок-сервисы внешних источников
Vibe Security, «Умный кредитный кабинет». Исполнитель: Антон Шкель. Версия от 22.10.2026. Готовность к интеграции: 24.10, заморозка: 26.10.

## 1. Зачем нужны моки
Скоринг берёт данные о клиенте из пяти источников: ЕГРЮЛ/ЕГРИП, ФНС («Прозрачный бизнес»), БКИ, внутренние данные банка и параметры заявки. Первые четыре в реальности являются внешними системами, доступа к ним у нас нет. Моки отдают синтетические данные по ИНН так, как это делали бы настоящие сервисы, включая задержки и сбои. На них держатся три вещи:
- умный старт (H1): по ИНН заполняется карточка компании;
- скоринг и решение: из ответов моков бэкенд считает 10 факторов и балл;
- надёжность: на демо мы показываем, что заявка не падает, когда источник тормозит или недоступен.

Моки отдают только сырые данные. Баллы, грейды и решение считает бэкенд (модуль скоринга на Kotlin). В моках никакой логики скоринга нет.

## 2. Технология
Берём WireMock в отдельном контейнере. Код писать не нужно: каждый ответ описывается JSON-файлом. Готовый комплект лежит в папке «Код/mocks» и в архиве mocks.zip: маппинги, ответы для семи ИНН, README и кусок docker-compose. Если Дмитрий захочет сделать моки модулем внутри Spring, контракты из этого ТЗ остаются теми же.

```
mocks:
  image: wiremock/wiremock:3.9.1
  ports: ["8089:8080"]
  volumes: ["./mocks:/home/wiremock"]
  command: ["--global-response-templating", "--verbose"]
```

Структура папки в репозитории:

```
mocks/
  mappings/     какой запрос → какой ответ (по файлу на сервис и ИНН)
  __files/      тела ответов: egrul/, fns/, bki/, bank/
  README.md     список ИНН, сценарии, команды проверки
```

Требования:
- тег образа фиксированный, не latest;
- все ответы в UTF-8 с заголовком Content-Type: application/json; charset=utf-8;
- поля в camelCase, суммы в рублях целыми числами, даты в формате ГГГГ-ММ-ДД;
- данные только синтетические, никаких реальных людей и компаний;
- бэкенд обращается к мокам по адресу http://mocks:8080 внутри compose, снаружи мок доступен на порту 8089.

## 3. Сервисы и контракты
### 3.1. ЕГРЮЛ / ЕГРИП
GET /egrul/v1/companies/{inn}
Даёт фактор 1 (возраст бизнеса) и фактор 7 (отрасль по ОКВЭД), заполняет карточку компании на шаге «Умный старт».

```
{
  "inn": "7703168426",
  "ogrn": "1227700512764",
  "type": "LEGAL",
  "shortName": "ООО «Хлебный двор»",
  "fullName": "Общество с ограниченной ответственностью «Хлебный двор»",
  "status": "ACTIVE",
  "registrationDate": "2022-03-12",
  "okved": { "code": "10.71", "name": "Производство хлеба и хлебобулочных изделий" },
  "smeCategory": "MICRO",
  "director": { "fullName": "Ковалёва Мария Сергеевна", "position": "Генеральный директор" },
  "address": "г. Москва, ул. Пекарская, д. 7",
  "flags": { "massAddress": false, "unreliableInfo": false }
}
```

- type: LEGAL (юрлицо) или IP (ИП).
- status: ACTIVE, IN_LIQUIDATION, LIQUIDATED, BANKRUPT.
- smeCategory: MICRO, SMALL, MEDIUM.
- Если ИНН не найден: 404 и тело {"code": "NOT_FOUND", "message": "Компания с таким ИНН не найдена"}.

### 3.2. ФНС, «Прозрачный бизнес»
GET /fns/v1/companies/{inn}/finance
Даёт фактор 2 (выручка), фактор 6 (налоговая задолженность) и половину фактора 3 (выручка в знаменателе нагрузки).

```
{
  "inn": "7703168426",
  "reportYear": 2025,
  "revenue": 15000000,
  "profit": 1200000,
  "taxDebt": 0,
  "accountsSuspended": false,
  "taxRegime": "USN"
}
```

- accountsSuspended: true означает, что ФНС приостановила операции по счетам. Это стоп-фактор.
- taxRegime: OSN, USN, PSN, ESHN.

### 3.3. БКИ
POST /bki/v1/reports
Даёт фактор 3 (долг в числителе нагрузки), фактор 4 (просрочки) и фактор 5 (количество кредитов). По 218-ФЗ кредитный отчёт можно запросить только при согласии клиента, поэтому без consentId мок отвечает отказом.

Запрос:

```
{ "inn": "7703168426", "consentId": "c0a8-0001", "consentSignedAt": "2026-10-25T10:00:00Z" }
```

Ответ 200:

```
{
  "inn": "7703168426",
  "reportDate": "2026-10-25",
  "activeLoans": [
    { "lender": "Банк 1", "type": "TERM_LOAN", "balance": 4000000, "monthlyPayment": 190000, "openedAt": "2024-05-10" },
    { "lender": "Банк 2", "type": "TERM_LOAN", "balance": 3500000, "monthlyPayment": 165000, "openedAt": "2025-02-01" },
    { "lender": "Лизинг 1", "type": "LEASING", "balance": 1800000, "monthlyPayment": 95000, "openedAt": "2025-06-15" }
  ],
  "totalDebt": 9300000,
  "monthlyDebtPayments": 450000,
  "overdues": [ { "days": 3, "date": "2025-10-14", "closed": true } ],
  "maxOverdueDays24m": 3,
  "inquiries30d": 4
}
```

- Без consentId: 403 и {"code": "CONSENT_REQUIRED", "message": "Нет согласия на запрос кредитной истории"}.
- Названия кредиторов обезличены («Банк 1», «Лизинг 1»): реальные банки в синтетике не упоминаем.

### 3.4. Внутренние данные банка
GET /bank/v1/clients/{inn}
Даёт фактор 10 (обороты в банке). Помесячные поступления нужны для прогноза кассового разрыва (H6), если до него дойдём.

```
{
  "inn": "7703168426",
  "isClient": true,
  "clientSince": "2024-10-01",
  "relationshipMonths": 24,
  "avgMonthlyInflow": 1250000,
  "monthlyInflows": [1100000, 1180000, 1320000, 1250000, 1190000, 1300000, 1280000, 1210000, 1350000, 1240000, 1220000, 1360000]
}
```

Если клиент не обслуживается в банке: isClient false, relationshipMonths 0, массив поступлений пустой.

### 3.5. SMS (вход в кабинет и подпись)
POST /sms/v1/send
Принимает {"phone": "+79990000000", "text": "Код: 1234"} и всегда отвечает 200 {"messageId": "sms-0001", "status": "SENT"}. Код генерирует бэкенд; в демо-профиле он всегда 1234, как на схеме пути пользователя. Мок только делает вид, что отправил SMS.

### 3.6. Выдача денег (Should)
POST /payments/v1/disbursements
Принимает {"applicationId": "...", "amount": 3000000, "account": "40702810000000000001"} и через 2 секунды отвечает 200 {"paymentId": "pay-0001", "status": "COMPLETED"}. Нужен, чтобы заявка дошла до статуса FUNDED.

### 4.2. Как бэкенд посчитает факторы по этим данным
Таблица нужна, чтобы проверить моки: если цифры в ответах верные, у каждого профиля получится именно такая сумма баллов. Веса взяты из таблицы факторов команды.

| Фактор | ТехноПрогресс | Хлебный двор | СтройМаркет |
|---|---|---|---|
| 1. Возраст бизнеса | 8 лет: +25 | 4 года: +25 | меньше года: −50 |
| 2. Выручка | 50 млн: +30 | 15 млн: +30 | 5 млн: +15 |
| 3. Нагрузка (долг к выручке) | 10%: +20 | 62%: −40 | 80%: −40 |
| 4. Просрочки в БКИ | нет: +10 | до 30 дней: −20 | больше 30 дней: −50 |
| 5. Количество кредитов | 1: −10 | 3: −30 | 1: −10 |
| 6. Налоговая задолженность | нет: +10 | нет: +10 | есть: −30 |
| 7. Отрасль | ПО: 0 | хлеб: 0 | стройка: −15 |
| 8. Сумма к выручке | 20%: 0 | 33%: 0 | 60%: −20 |
| 9. Залог | нет: 0 | нет: 0 | нет: 0 |
| 10. Клиент банка больше года | да: +15 | да: +15 | нет: 0 |
| Сумма баллов | +100 | −10 | −200 |

Как из суммы получить балл 0–1000, решают Лиза и Марина. Наше предложение и расчёт лежат в инструкциях команде, раздел про скоринг. При предложенной формуле (600 + 2 × сумма баллов) профили получают 800 (A), 580 (C) и 200 (D).

## 5. Сбои и задержки
- Задержка: в маппинге "fixedDelayMilliseconds": 10000.
- Ошибка сервера: "status": 503 с телом {"code": "UNAVAILABLE"}.
- Обрыв соединения: "fault": "CONNECTION_RESET_BY_PEER". Его можно показать жюри вручную через админку WireMock.
- Сначала сбой, потом успех: сценарий WireMock (scenarioName, requiredScenarioState, newScenarioState). Перед каждым прогоном демо состояние сбрасывается командой POST /__admin/scenarios/reset.
- Любой неизвестный ИНН в ЕГРЮЛ получает 404 через маппинг с низким приоритетом и шаблоном пути /egrul/v1/companies/.*.

Пример маппинга:

```
{
  "request": { "method": "GET", "url": "/egrul/v1/companies/7703168426" },
  "response": {
    "status": 200,
    "headers": { "Content-Type": "application/json; charset=utf-8" },
    "bodyFileName": "egrul/7703168426.json"
  }
}
```

## 6. Что согласовать до начала работы
- С Дмитрием: пути и названия полей из раздела 3, базовый адрес в application.yaml, таймауты на клиентах (предлагаем 3 секунды и 2 повтора только для GET).
- С Лизой и Мариной: веса факторов, границы интервалов (5 млн выручки попадает в «5–10 млн»; ровно 30 дней просрочки ещё дают −20; клиент ровно 12 месяцев уже получает +15, как в коде команды) и формулу перевода суммы баллов в шкалу 0–1000.
- С Мариной: заменить ИНН в сид-данных на ИНН из раздела 4. В текущем файле 7707083893 и 7710140679 принадлежат реальным крупным банкам, а у 7712345678 неверная контрольная сумма, и валидация ИНН его не пропустит.
- С Владимиром: на экранах использовать те же компании и цифры, что отдают моки.

## 7. Как проверить готовность
```
docker compose up -d mocks
curl http://localhost:8089/egrul/v1/companies/7703168426
curl http://localhost:8089/egrul/v1/companies/7718046237
curl http://localhost:8089/fns/v1/companies/7704983159/finance
curl -X POST http://localhost:8089/bki/v1/reports -H "Content-Type: application/json" -d "{\"inn\":\"7729501760\"}"
curl -X POST http://localhost:8089/__admin/scenarios/reset
```

Критерии приёмки:
- контейнер поднимается одной командой вместе с остальным compose;
- для всех семи ИНН ответы совпадают с таблицами раздела 4, русский текст читается без «кракозябр»;
- БКИ без согласия отвечает 403;
- задержка, 503 и сценарий «503, 503, 200» воспроизводятся каждый раз после сброса;
- по трём основным ИНН кабинет проходит путь до трёх разных решений: одобрение, контрпредложение, отказ;
- в README перечислены ИНН, сценарии и команды проверки.
